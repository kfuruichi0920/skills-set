# 整理の工程

## 1. 整理目的と入力の意味を確かめる

目的は「この素材を読んだ第三者が何を理解できればよいか」で定める。判断・提言・スライド化を必須にしない。用語整理だけ、未分類情報の整理だけ、依存関係の解明だけでも成果になる。

素材に情報単位IDを付け、出所と位置を記録する。必要な場合は短い抜粋を添える。対象、用語の定義、属性、関係の種類・方向、時間、状態、イベント、条件、数値、目的、根拠を抽出する。事実・解釈・仮説・試算・不明を区別する。

概念の混同がある場合は用語と定義を先に整理し、名称の一致だけで同一概念に統合しない。元の表現を残して、正規化したラベルとの対応を記録する。

完了条件: 主要情報に出所があり、意味が曖昧な箇所を特定できる。

## 2. 意味構造と整理軸を判定する

framework.mdの19軸を、構造情報・動的情報・判断情報の観点から検討する。入力にない軸を足して完成させる必要はない。

- 構造: identity、category、hierarchy、part_whole、relation、dependency、location。
- 動的: sequence、time、state、event。flowはこれらを使った表現形式。
- 目的・判断・観測: purpose、responsibility、quantity、risk、cause。
- 横断: evidence、confidence、trace。

この区分は探索の補助であり、軸は複数の区分にまたがってよい。条件・例外・境界・向き・単位・期間・粒度は、対象や関係の修飾情報として必ず保つ。

一つの階層では足りない場合は、情報 × 工程 × 対象 × 観点 × 状態などの独立したファセットで整理する。物理構成、機能構成、作業構成を混ぜず、必要ならそれぞれの分解と対応図を作る。多対多の関係はgraphやmatrixで保持する。

完了条件: 採用軸に入力の根拠があり、条件と重要な関係が残っている。

## 3. 表現形式と専門手法を選ぶ

最初にlist、table、tree、matrix、graph、sequence、timeline、state_model、flow、map、quantitative_chart、argumentから適した基本表現を選ぶ。専門手法は次に検討し、一般的な表・図で足りるなら専門名を付ける必要はない。

選択ルールを適用し、必要な情報があるか確認する。既存カタログに合わない場合は、カタログ外の表現や独自構成を採用できる。候補比較には採用形式・専門手法・必要データ・何が見えるか・見えにくいか・採否理由を記す。

一つで足りない場合は複合表現にする。例えば、依存graph＋状態条件table＋失敗影響tableで「構成上の依存」「条件による振る舞い」「影響の整理」を分担する。共通の対象IDで接続し、同じ情報を複数箇所に書く場合は不一致を確認する。情報量が大きいことだけを理由に、全専門手法を並べない。

完了条件: 主案と代替案の違いを説明でき、採用する手法の前提と不足情報が明示される。

## 4. 読み手に合う説明とキャンバスを選ぶ

情報モデルと説明レイヤを分ける。情報の内容と条件を保ったまま、読み手の問いに合わせて順序・粒度・強調を調整する。

| 読み手の関心 | 説明に残すもの | 組み立ての例 |
| --- | --- | --- |
| 設計者 | 関係種別、条件、状態、境界、追跡ID | 全体構造 → 詳細関係 → 条件・例外 |
| PM・調整役 | 作業、時期、依存、責任、不明点 | 全体像 → 依存と担当 → 次に確認する事項 |
| 顧客・利用者 | 目的、振る舞い、影響、利用条件 | 背景 → 仕組み → 利用上の意味 |
| 判断する人 | 問い、選択肢、基準、証拠、留保 | 問い → 比較 → 判断と未確定事項 |
| 予備知識が少ない人 | 定義、要点、具体例、全体との対応 | 概要 → 用語 → 具体例 → 詳細 |

Pyramid、SCQA、PREP、IBIS、Claim–Evidence–Reasoning、Overview → Detailなどは説明の候補であり、情報モデル自体の代わりにしない。形式を守るために結論や対立を捏造しない。

スライド風キャンバスは「領域を分け、情報のまとまりを一度に読める」場合に適している。長い用語表、詳細なトレース行列、編集可能な情報モデルには、文書・表・図・構造化データが適切な場合もある。指定された形式を尊重し、密な資料は概要キャンバスと詳細付録に分ける。

完了条件: 選んだ出力の理由を説明でき、重要な情報を無理に一枚へ詰めていない。

## 5. 整理結果と根拠記録を出す

整理結果の元となる情報単位と、図・表・領域に要素IDを付ける。根拠記録は以下の対応を残す。

入力・出所 → 正規化した対象と関係 → 検出した軸と目的 → 候補表現・手法 → 採否と前提 → 出力要素。

補足には、観測事実、明示した解釈、比較上の判断基準、採否理由、省略と未確定事項を簡潔に書く。曖昧な情報を都合よく補完した説明を記録しない。主成果物と別Markdownに保存するのを標準とし、指定があれば付録や別形式にする。

完了条件: 第三者が出所と選択理由をたどり、解釈を変更したときに影響する出力箇所がわかる。

## 6. 内容と表現を検証する

- 情報: 用語、事実、仮説、条件、例外、境界、多対多、方向を確認する。
- 軸: timeとsequence、processとstate、hierarchyとpart_whole、relationとcauseを区別する。
- 数値: 単位、分母、期間、合計、尺度、試算前提を確認する。
- 手法: 必要入力、記法、計算前提、未実施の分析を確認する。
- 追跡: 元情報IDと出力要素ID、採否理由、省略理由を確認する。
- 説明: 読み手が要点と留保を理解できるか確認する。
- 見た目: 完成ファイルでは全領域を表示し、欠け・重なり・読みにくさを直す。

色、フォント、余白、文字サイズ、キャンバス寸法は用途から選ぶ。数量を表す長さ・面積は比例させ、比較では尺度と位置を揃える。線・塗り・色の意味を一貫させる。

完了条件: 重要情報が対応付けられ、未検証・不明・省略を表示して提出できる。
